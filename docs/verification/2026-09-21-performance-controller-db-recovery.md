# 性能控制器数据库断线恢复

## 问题与处理

2026-09-21 11:19 左右，控制器续租时连接 MySQL 出现 `OperationalError(2003)` / `No route to host`，异常逃出主循环；退出清理再次访问数据库，继续报错。之后数据库恢复可访问，但控制器进程已退出，管理器又处于禁止自动重启状态，页面持续提示“性能控制器未在线”。

临时数据库连接异常现在由控制器进程自行处理，不依赖服务管理器再次启动进程：

- 启动时数据库不可用也进入重试循环；连接与传输异常会关闭旧连接，暂停调度并重新连接。重试间隔逐步增加到 30 秒，持续故障不会刷屏输出原始数据库异常或凭据。
- 仅控制器进程将 MySQL 连接、读和写超时限制在 5 秒以内；其他后端服务的数据库配置不变。
- 发生数据库或租约故障时先停止本地监督进程，确认其退出后才允许创建新的控制器实例、重新申请全局租约。仍有效的旧租约不可覆盖。
- 重新获得租约后沿用现有孤立运行回收流程：已有活动运行收到停止指令、最终标记执行不完整；不重新发送准备指令、不自动重跑。排队运行在旧运行安全结束后才能继续调度。
- 初始启动遇到另一健康控制器仍拒绝争用租约；账号错误、SQL 和表结构错误不会被误当作网络故障无限重试。
- 退出信号可以中止重连等待。数据库不可用时的退出仍停止本地进程，剩余租约自行过期，不再要求数据库清理成功才能退出。

未修改节点固定执行脚本、版本、数据库结构、现场计划或节点身份。已发布的 0.3.1 镜像与固定模板哈希保持一致。

## 边界

没有人为中断现场数据库或对业务目标发压；断线恢复行为通过隔离故障注入验证，现场只核对控制器上线与持续心跳。服务管理器的进程身份判定仍是独立待办；本次通过保持控制器进程存活解决临时数据库故障的恢复，不改变其他程序崩溃后的重启上限。
