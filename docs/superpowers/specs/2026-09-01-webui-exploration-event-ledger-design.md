# WebUI MCP 探索事件账本与 Python 脚本生成重构

## 文档状态

- 状态：已实施，待真实页面联调验收
- 日期：2026-09-01
- 目标：移除“由探索智能体最终输出严格 JSON 证据”的单点失败，改为平台自动记录浏览器轨迹并据此生成 Python 脚本
- 范围：WebUI AI 脚本生成主流程、探索结果展示、静态质量检查和有限修复
- 非范围：Python 脚本真实调试执行器、测试用例/套件执行模型、API/App 自动化

## 1. 问题与目标

当前流程要求同一个 MCP 智能体完成页面操作、记忆探索结果，并在最后一次回复中输出完整且严格符合 `ExplorationSnapshot` 的 JSON。浏览器探索即使已经成功，只要最终回复是普通文本、JSON 字段不完整或模型在最后一步中断，平台就会丢弃语义证据并停止生成 Python。

目标流程调整为：

```text
用户测试目标
  → Playwright MCP 探索页面
  → 平台 callback 自动记录每次工具调用和页面观察
  → 平台整理紧凑探索轨迹
  → 独立模型调用生成 Python Playwright 脚本
  → 静态质量检查
  → 最多两轮有限修复
  → 用户检查、调试和保存
```

MCP 智能体的最终文本不再承担数据契约。它可以仅表示“本轮已停止探索”，平台也不会解析其中的 JSON 或 Python。

## 2. 方案对比

### 方案 A：让 MCP 智能体探索后直接输出 Python

优点是调用次数少、改动表面较小。缺点是页面证据仍只存在模型上下文中；最终 Python 截断、代码围栏错误、模型超限或服务异常时，整轮探索仍然丢失。探索动作、失败尝试和最终脚本也难以区分，不能稳定恢复。

### 方案 B：平台事件账本 + 独立 Python 生成器（推荐）

平台 callback 记录真实工具输入、结果和页面观察，MCP 最终文本被忽略。探索结束、超时或部分失败后，只要存在最低可用轨迹，就把场景和轨迹交给现有 `ScriptGenerator` 生成 Python，再执行质量检查和修复。

优点是探索成果不再依赖最后一段模型输出；模型服务在生成阶段失败时，可以只重试 Python 生成，不需要重新操作网页。缺点是需要设计轨迹压缩、敏感值处理和 MCP 参数到 Python 定位器的转换规则。

### 方案 C：完全确定性地把 MCP 调用转换为 Python

不使用脚本生成模型，直接逐条翻译 MCP 工具调用。它对简单点击、填写可行，但无法可靠删除探索绕路、补充业务断言、生成清理逻辑或处理不同 MCP 工具参数，第一版成本高且脚本可读性差。

本次采用方案 B；对稳定工具调用使用确定性规范化，对业务步骤、断言和清理代码仍使用独立脚本生成模型。

## 3. 平台自动记录的数据

新增平台生成的 `ExplorationTrace`，继续保存在现有 `WebUIScriptGeneration.exploration_snapshot` JSON 字段中，不要求数据库迁移。旧探索 JSON 不做兼容；开发环境可清理旧生成记录。

```text
ExplorationTrace
├── schema_version = 2
├── start_path
├── events[]
│   ├── sequence
│   ├── tool_name
│   ├── category: navigate | observe | interact | screenshot | error
│   ├── status: succeeded | failed | blocked
│   ├── relative_path
│   ├── locator                  # 结构化定位信息，不保存凭据值
│   ├── input_summary            # 点击目标、按键、选择项等
│   ├── output_excerpt           # 有长度上限的可见文本/HTML 摘要
│   ├── state_fingerprint
│   └── screenshot_path
├── observed_paths[]
├── successful_interactions[]
├── failed_interactions[]
├── coverage
├── cleanup
├── tool_stats
└── warnings[]
```

记录规则：

1. `on_tool_start/on_tool_end/on_tool_error` 是唯一可信来源，不采用模型自报的计数、页面或操作结果。
2. 导航、点击、填写、选择、按键和页面读取均记录；重复的页面读取按指纹去重。
3. 填写值默认不持久化。密码、Token、Cookie、账号等替换为变量引用；普通业务值记录为“运行时测试数据”，脚本重新使用 `time.time_ns()` 生成。
4. 页面输出只保留生成定位器和断言所需的有界摘要，不保存无限制完整 DOM；交互前后的关键观察优先保留。
5. 成功交互与失败尝试分开。失败定位器只作为负面证据，不能直接写入最终脚本。
6. 每个任务继续保留独立 JSONL 轨迹文件，正常结束或异常捕获时汇总写入数据库。最终模型文本无论是否为 JSON，都不影响轨迹保存。

## 4. 探索完成与降级规则

不再要求平台先得到“完整证据 JSON”才能进入 Python 生成。

### 可以进入脚本生成

- 至少有一次成功导航或有效页面观察；
- 至少保留一个可用页面状态；
- 没有命中审批、付款、发布、越权文件操作等强制终止边界。

探索完整时生成普通草稿；探索因总时限、工具预算或部分定位失败结束，但已有可用轨迹时，仍生成草稿，并把状态标记为“需要检查”，不得伪装成完整探索。

### 不生成脚本

- 浏览器未启动或目标页面完全不可达；
- 没有任何有效页面观察；
- 登录失败且没有进入业务页面；
- 命中审批、付款、发布、越权文件操作等禁止动作或安全边界。

写入或清理结果未知时仍保留并生成可检查草稿，但任务状态必须是“需要检查”，不能标记为可直接使用。

### 不自动重放

探索发生过可能的写操作后，worker 中断、提交结果未知或清理未知时，不从头重跑浏览器。平台保留轨迹、继续整理可检查草稿，并显示最后成功阶段、可能残留和人工检查建议。

## 5. Python 生成与修复

`ScriptGenerator` 输入由 `ScenarioSpec + ExplorationSnapshot` 改为 `ScenarioSpec + ExplorationTrace`：

1. 仅使用成功交互中的定位信息；
2. 删除探索过程中的绕路、重复读取和失败尝试；
3. 根据场景步骤整理可重复执行的 Python Playwright 流程；
4. 使用相对路径、`async def run(page)`、环境变量登录信息和运行时唯一测试数据；
5. 每个动作、断言和清理保留中文注释；
6. 对缺少必要定位证据的步骤不得猜测。

现有 AST/tokenize 质量检查继续使用，但证据相关检查改为轨迹覆盖检查：

- 场景步骤必须能映射到脚本步骤注释；
- 最终脚本中的业务定位器必须来源于成功工具调用或有效页面观察；
- 写操作必须有 `try/finally` 和清理注释；
- 账号密码不得成为字符串字面量；
- 缺失必要步骤是阻断项，不再只是普通警告。

最多两轮静态修复继续复用同一探索轨迹，不重新打开 MCP 浏览器。模型服务在 Python 生成或修复阶段失败时保留探索轨迹，并允许后续只重试当前阶段。

## 6. 用户界面调整

生成时间线保持“探索页面 → 生成 Python → 检查质量 → 自动修复”，但“探索证据”改名为“探索轨迹”。

探索轨迹展示：

- 到达过的页面和相对路径；
- 成功动作、失败尝试和最后完成位置；
- 关键定位信息；
- 截图；
- 是否因超时、预算、登录或安全边界提前结束；
- 是否存在未清理测试数据。

失败提示必须区分：

- `页面未打开，无法生成`；
- `已探索到新增表单，但尚未完成提交/编辑/删除，已生成待检查草稿`；
- `页面探索完成，Python 生成服务暂时不可用，可仅重试脚本生成`；
- `脚本已生成，但质量检查仍有阻断项`。

不再向用户展示“探索证据 JSON 格式错误”，因为该格式不再由模型负责。

## 7. 主要风险与处理

1. **MCP 参数不能一对一转换为 Python 定位器**：增加按工具类型的规范化适配器；未知参数保留为未支持证据，不猜测。
2. **探索动作包含绕路**：仅把成功且与场景目标相关的交互提供给脚本生成器；失败和重复动作单独保存。
3. **页面内容过大**：按页面状态指纹去重，单事件和总轨迹设置字符上限，优先保留交互前后观察。
4. **敏感值泄露**：在 callback 进入持久化前处理，而不是写入后再脱敏；填写值只保留变量类型，不保留真实值。
5. **模型过早停止**：轨迹覆盖率用于提示和质量门禁，但不再让一个不完整 JSON 阻断所有成果；有最低证据时生成待检查草稿。
6. **动态页面定位器失效**：保留成功工具调用、页面观察和截图；真实执行失败仍需用户调试，不能把静态生成标为运行通过。
7. **探索写入后异常退出**：继续使用任务命名空间、写操作台账和清理状态；未知结果不重放，向用户明确提示残留风险。
8. **轨迹持久化影响性能**：callback 只做有界内存记录和追加文件写入，数据库在阶段边界批量更新，避免每个异步工具回调直接调用 ORM。

## 9. 验收标准

1. MCP 最终返回普通文本、空文本或 Markdown 时，只要工具轨迹有效，仍进入 Python 生成。
2. 浏览器工具超时或达到预算后，已有轨迹不会丢失；有最低证据时产生待检查草稿。
3. 生成 Python 不包含探索凭据、完整 URL、失败定位器或探索用的具体测试数据。
4. 每个业务动作和断言有中文注释，写操作包含 `finally` 清理。
5. Python 生成服务失败时不重新探索页面，可以基于已保存轨迹重试。
6. 页面能明确看到探索到哪里、最后失败在哪里、是否存在写入或清理风险。
7. 离线后端测试覆盖成功、非 JSON 终答、超时、工具失败、模型失败、清理未知和只重试生成；前端测试和生产构建通过。

当前自动验收：后端离线回归 237 项、前端单元测试 23 项及生产构建均通过；真实页面探索和生成效果仍需在部署环境中验证。

实施前先提交当前工作区。代码回退恢复旧编排器即可；`exploration_snapshot` 继续是 JSON 字段，不需要逆向数据库迁移。回退不会撤销探索期间已经写入的测试环境数据，存在残留时仍需人工清理。
