## 服务管理器进程身份待办（2026-09-21）

- 0.3.1 发布前后，后端、Celery、控制器和 Caddy 健康探针均可通过，但管理器出现“未纳管”状态；新启动的三项服务也在后续检查中被标为未纳管，进程 PID 未变化。

- 2026-09-21 已单独修复性能控制器的数据库断线恢复：临时连接故障由控制器进程自行重连，恢复后重新申请租约并回收中断运行；不会因数据库断线消耗管理器的进程重启次数。本项进程身份问题仍待处理，不视为已修复。见 [数据库断线恢复验收](verification/2026-09-21-performance-controller-db-recovery.md)。

## API 自动来源确认与 HTTP 重定向

- 发现日期：2026-09-09。
- 范围：API 网页探索自动模式的跨主机来源确认；不是 requests 执行层或 UI 脚本生成层。
- 根因：当前 Chromium Playwright 路由仅将首跳交给 `context.route`，已放行请求的后续 HTTP 重定向由浏览器继续，不能靠首跳授权宣称拦截了全部网络请求。307/308 可能转发原方法与正文。
- 本次处理：直接 fetch/XHR 请求支持发送前确认，重定向后续仅保留受限元信息，不作为完整可执行证据；页面和使用文档明确标注仅限可信测试站点，不支持把此机制当作重定向或 SSO 的安全隔离层。
- 已知风险：重定向请求可能在用户审批前已经发出，元信息记录不能撤销网站写入。不能通过重复登录、代理重放或补抓正文掩盖此限制。
- 后续根因方案：单独评估 Chromium CDP 响应阶段 Fetch 拦截与 Playwright 路由的交互，在重定向发生前确认目标；须测试 302/303/307/308、相对 Location、多跳、Cookie、方法与正文保留、取消及无重放，再改变支持范围。本次未引入该底层架构改动。
- 2026-09-12 回归：已补齐直接文档导航和新窗口首请求的来源检查。尝试响应代取后发现 Chromium 将内网页面当作合成响应，导致原本可用的回环 API 被网络地址空间策略拒绝；该实现已撤回，不授予额外浏览器权限、不禁用网络安全功能。11 项采集测试（含真实 Chrome）通过；重定向仍保持上述边界。

## Element Plus 数字输入框动态禁用状态

- 发现日期：2026-09-09。
- 范围：API 网页探索页的探索总时限输入框。
- 触发：输入框初次挂载时页面仍在加载，`disabled=true`；随后解锁。
- 本地证据：当前安装版本 `element-plus/es/components/input-number/src/input-number2.mjs` 只在 `onMounted` 写入内部输入框的 `aria-disabled`，`onUpdated` 只更新 `aria-valuenow`。实际可编辑状态恢复，但可访问性状态仍为禁用。
- 当前处理：按禁用状态为该数字输入框设置组件 key，状态变化时重建控件，使原生状态与 ARIA 状态同步；数值由父级 `v-model` 保留。不改依赖包文件，不升级全项目依赖，不强制绕过浏览器的可用性检查。
- 边界：切换禁用状态会重建该控件并丢失其焦点；加载或提交期间本就不允许输入，已输入数值仍保留。
- 后续：统一升级组件库时，验证动态 `aria-disabled` 已修复后移除此局部处理，保留浏览器回归测试。
