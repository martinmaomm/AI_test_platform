# WebUI 完整探索与可验证元素证据设计

## 文档状态

- 状态：已实施，待真实页面联调验收
- 日期：2026-09-01
- 目标：提高 AI 生成 Python Playwright 脚本的定位器准确率，避免在探索不完整或证据不足时生成看似完整、实际不可执行的脚本
- 范围：MCP 页面探索、探索轨迹、元素证据、脚本生成输入、静态质量门禁和离线回归测试
- 非范围：自动执行生成脚本、自动修改真实业务数据、前端页面大改、测试用例与套件执行模型

## 1. 已确认问题

当前流程虽然仍是“先探索、后生成”，但中间只保留有界工具轨迹：

1. `explore_until_complete` 实际只运行一轮智能体；模型提前结束时，平台会接受部分轨迹。
2. 只要存在最低页面状态，即使必要场景步骤全部缺失，也会继续生成 Python 草稿。
3. 生成器最多接收 8,000 字符的压缩轨迹，交互上下文和页面语义可能被截断。
4. 工具轨迹保存的是当次 MCP selector，不是经过验证的稳定元素清单；动态 ID、宽泛可见元素和组合 selector 容易进入生成阶段。
5. 现有质量检查主要在整段成功轨迹文本中查找定位器字面量，无法证明脚本定位器来自某个确定的成功元素证据。

## 2. 目标流程

```text
场景规范化
  → Playwright MCP 在同一浏览器会话探索
  → 平台记录原始工具轨迹
  → 计算场景步骤覆盖
  → 未覆盖时在同一会话定向补探（有界）
  → 平台确定性生成 ElementEvidence JSON
  → 元素证据和步骤覆盖满足要求
  → 生成 Python Playwright
  → 精确定位器溯源和脚本静态检查
  → 用户检查、手动调试和保存
```

本次恢复 JSON 中间层，但 JSON 由平台从真实 Playwright callback 构建，不解析 MCP 智能体最终文本，也不允许模型自由编造页面元素。

## 3. 元素证据契约

继续使用现有 `exploration_snapshot` JSON 字段，不增加数据库迁移。`ExplorationTrace` 升级并增加 `element_evidence`：

```text
ElementEvidence
├── evidence_id              # 由成功事件序号确定，例如 E000012
├── source_sequence          # 原始工具事件序号
├── scenario_step_ids[]      # 可映射的场景步骤
├── relative_path
├── tool_name
├── action                   # click/fill/select/press/observe
├── locator_kind             # css/role/text/label/placeholder/testid
├── locator_value            # 已验证定位值或规范化模板
├── locator_kwargs           # role/name/exact 等结构化参数
├── runtime_placeholders[]   # 运行时唯一数据占位符
├── stability               # stable/acceptable/fragile/rejected
├── result_excerpt
└── state_fingerprint
```

规则：

1. 只有成功工具调用可以产生可执行元素证据；失败 selector 只保留在原始轨迹中。
2. 优先级为 `testid`、`role + accessible name`、`label`、`placeholder`、稳定属性 CSS、精确文本。
3. 动态 ID、裸 `input:visible`、无上下文 `nth()`、过深层级和过宽文本默认标记为 `fragile` 或 `rejected`。
4. 探索命名空间在 selector 中规范化为 `{run_id}`，生成脚本时替换为本轮运行时唯一变量，不能复用探索数据。
5. 每个脚本业务定位器必须能够回指一个 `evidence_id`；生成器不能拼接未被证据支持的新定位器。

## 4. 完整探索规则

1. 第一轮按完整场景探索，平台忽略智能体最终文本，只读取真实工具调用。
2. 第一轮结束后计算步骤覆盖；存在缺失步骤时，在同一个 MCP 浏览器会话中最多补探两轮。
3. 补探提示只包含缺失步骤、当前相对路径、已确认步骤和剩余预算，不要求重做已经成功的写操作。
4. 总工具调用、模型步骤和总时间仍使用同一份全局预算；补探不会重置预算。
5. 登录失败、连续定位失败、重复操作、写入结果未知和安全策略命中仍立即终止。
6. 完成标准不再是“智能体返回最终文本”，而是所有必要步骤存在成功证据，并且动作步骤至少有一个可用元素证据。
7. 补探结束仍缺少证据时，不生成伪完整脚本；任务进入 `needs_review`，明确列出缺失步骤和脆弱定位器。

## 5. 生成与质量门禁

生成器输入调整为：

- 场景步骤；
- 按时间排序的结构化元素证据；
- 必要的页面状态摘要；
- 步骤到 `evidence_id` 的映射；
- 清理状态和告警。

生成规则：

1. 优先原样使用成功且稳定的定位器。
2. 允许把 `{run_id}` 确定性替换为脚本运行时变量，不允许模型自由改写 selector 结构。
3. 每个业务动作注释增加证据引用，例如 `# 步骤 2：打开新增用户表单 [E000012]`。
4. 没有元素证据的步骤不得生成定位代码。
5. 静态门禁按定位器规范化签名做精确匹配，不再用整段文本包含关系判断。
6. 自动修复只能使用同一份证据中的其他允许定位器；缺少替代证据时保留阻断项，不扩大重写。

## 6. 本次实施边界

本次完成：

- 同会话有界补探；
- 元素证据构建、稳定性分类和 JSON 持久化；
- 生成器优先消费元素证据；
- 精确定位器溯源；
- 缺失完整证据时阻止伪完整脚本；
- 对应离线回归测试。

本次不自动运行生成脚本。自动运行可能再次执行新增、编辑、删除，与当前“用户先检查、再手动调试”的产品流程冲突；待本轮真实页面验证定位器质量后，再单独设计隔离执行和失败定位器定向修复。

## 7. 验收标准

1. 智能体在登录中途提前结束时，平台会在同一浏览器会话继续补探，而不是立即生成脚本。
2. 必要步骤未覆盖时，页面明确显示待检查原因，不产生可保存、可执行的伪完整脚本。
3. `element_evidence` 只包含成功调用，不包含失败 selector、明文凭据或完整 URL。
4. 动态 Element Plus ID 和裸 `input:visible` 不会被当作稳定首选定位器。
5. 生成脚本中的静态业务定位器均可精确追溯到元素证据；未溯源定位器是阻断项。
6. 现有流式模型调用、超时配置、取消、写操作范围、清理状态和仅重试生成能力保持有效。
7. WebUI 生成链路离线测试通过，`git diff --check` 通过。

当前自动验收：WebUI/AI Core 离线回归 259 项通过；本次无数据库迁移。真实页面的元素准确率和供应商模型表现仍需部署环境验证。

本次不修改数据库 Schema。回退代码提交即可恢复 schema v2 工具轨迹生成；已有 JSON 中的新增字段会被旧代码忽略。探索已经造成的测试环境数据变化不会随代码回退自动撤销，仍以任务清理状态为准。
