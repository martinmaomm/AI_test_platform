# 分布式性能测试设计（平台端 + 压测节点端）

创建：2026-09-15；更新：2026-09-16。

状态：用户已确认总体架构，尚未开始性能模块开发。2026-09-16 追加确认：节点客户端在当前项目内开发，兼容局域网节点、公网机器及混合部署；不依赖 VPN，节点通过公网加密连接接入平台。以下为设计约束，不代表公网接入已实现或通过实机验证。

核心约定：用户只部署「平台端」和「压测节点端」。节点安装包包含轻量 Agent 和 Locust Worker 运行环境；平台下发脚本及配置，Agent 接收、校验、准备文件并启动 Worker。Master 统一控制压力和汇总请求统计，不另建一套调度引擎。

已完成的首页调整（2026-09-15）：App 自动化入口改为「安全测试（开发中）」，描述为「检测应用安全风险与常见漏洞，提供修复建议。」；性能测试、安全测试均继续置灰且不可点击。旧 App 业务代码未删除，压测客户端未部署，也未向被测网站发起压测。

## 1. 现状与目标

- 当前性能工作区是占位页面，后端尚无节点注册、压测调度、统计汇总业务。`backend/requirements.txt` 已声明 `locust==2.43.3`，但有依赖不等于已集成。
- 目标是平台管理测试计划、节点、运行及报告；节点实际发压，不让请求流量经过 Django。
- UI/API 自动化继续沿用原流程，性能模块独立执行。既有全局串行偏好建议解释为「不同压测运行排队」；同一次压测必须允许多个虚拟用户并发，各用户内部业务步骤可按顺序执行。

## 2. 路线比较

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 平台简单接入 Locust，节点手动启停 | 快速验证引擎和压测脚本 | 节点运维、项目权限、历史报告体验分散，不满足完整中控需求 |
| 平台端 + 压测节点端，内部复用 Locust（已选定） | 自己控制产品体验，复用成熟的用户调度、分布式通信及统计 | 需补齐轻量进程管理、任务一致性和平台报告，不建设完整设备运维系统 |
| 整套自研请求与分布式引擎 | 完全自由 | 需要自行处理并发、限流、连接复用、统计合并，维护与验证成本最高 |

采用第二种，不修改 Locust 源码，也不把它的网页作为第二套用户操作入口；只开发必要的适配和启动管理代码，并固定运行时版本。首版以项目现有版本作为候选基线，客户端镜像还需单独验证，不能直接复用平台整个 venv。

## 3. 两种部署包及内部职责

### 3.1 平台端：现有平台 + Locust Master

- **现有 Django/Vue**：项目权限、节点登记、计划及脚本快照、执行变量、运行排队、状态与报告。决定「哪个计划、哪些节点、多少用户、持续多久」，不自行把虚拟用户再分配一遍。
- **Locust Master**：平台内部的压测协调组件，每次运行使用隔离实例；唯一负责虚拟用户分配、压力爬升、正常开始/停止及请求统计汇总。不让用户另行操作 Locust 网页。
- **平台适配代码**：创建/回收 Master 独立进程，把一次运行的目标参数交给 Master，并将其状态及统计写回平台；不是另一个 Master。
- 部署包统一提供这几部分，但不把 Master 嵌入 Django 进程。首版可同机运行并限制资源，后续再拆机。Celery 只做短时间派发/核对，不让一次长压测占住现有 solo Worker。
- 平台部署包还包含 Locust RPC 的 TLS 接入组件，属于内部传输设施，不承担任务调度或统计汇总；不是第三套用户业务系统。

### 3.2 压测节点端：一个安装包，内含 Agent + Worker

- **轻量 Agent**：接收本节点的任务包，校验文件及版本，准备独立任务目录，启动/监控/回收 Locust Worker 进程；上报节点是否在线、准备是否成功、进程异常及有限诊断日志。保留必要的身份认证、资源信息和失联停止能力，不建设独立客户端管理平台。
- **Locust Worker**：由 Agent 启动后加载本轮脚本，连接 Master，按 Master 的指令模拟用户、向目标发送请求、记录并回传请求统计。首版每个节点默认一个 Worker 进程，多进程仅作为后续容量配置，不默认占满整台机器。
- Agent 与 Worker 是同一节点包里的两种职责，不要求用户分别安装或操作。Agent 不是 LLM 智能体，不生成/修改脚本、不转发 HTTP 请求、不分配压力，也不计算请求统计。
- Locust 的 Worker 心跳/连接状态用于判断执行器就绪；Agent 的在线状态只表明客户端能领取任务，不能替代 Worker 就绪检查，不重复实现 Locust 的运行期通信协议。

### 3.3 同仓开发、独立打包

- 节点源码放在当前仓库的独立 `performance-node/` 目录，拟包含 `src/performance_node/`、`tests/`、`pyproject.toml`、`Dockerfile`、`compose.yaml` 和节点部署说明。本次仅确定目录规划，不创建尚未可运行的空壳客户端。
- 节点有独立依赖、版本和构建入口，不安装整个后端 requirements，不导入 Django ORM、不携带平台 `.env`、数据库密码或模型密钥。Agent、Locust Worker 和支持的依赖一起进入节点镜像。
- 平台接口仍在后端维护，双方通过有版本的任务协议交互；统一校验协议、引擎和脚本包版本，版本不兼容时拒绝启动并提示升级，不以忽略字段的方式勉强运行。
- Docker Compose 管理常驻 Agent；Worker 按任务启动和回收。容器重启只恢复登记/心跳和异常任务核对，不自动重新执行中断的压测。注册状态及必要日志保存到限定的持久化目录。
- 节点包一并提供本地 TLS 转接组件及其生命周期管理，用户不手工拼装 Worker 和加密代理；不要求安装 VPN、配置全局代理或挂载宿主网络管理权限。

### 3.4 通信及唯一统计链路

- **准备与进程管理**：平台生成任务包 → Agent 主动通过认证 HTTPS 接口领取 → 校验并准备目录 → 启动 Worker。首版可用长轮询，不要求平台能够 SSH 到每台节点。
- **运行控制**：平台提交一次压测目标 → Master → 已就绪的 Worker。Worker 经节点包内的 TLS 转接组件连接平台加密入口，平台入口只转发至本轮 Master 的内部 Locust RPC 端口（默认 TCP 5557）；原生 RPC 不直接暴露公网。Worker 能否访问被测网站另行检查。
- **请求统计唯一链路**：Worker → Master 汇总 → 平台适配代码 → 平台保存及展示。Agent 只上报机器/进程状态和诊断日志，不另向平台上传一份相同的请求统计。
- **正常停止**：平台通知 Master 停止压测并收集尾部统计，之后 Agent 回收 Worker；失联、租约过期或进程失控时，Agent 才执行本地兜底终止，结果按实际完整性标记。正常负载控制和兜底回收不能变成两套并行调度。

Locust 原生 Master 负责控制和收集 Worker 统计，自身不发压；官方支持 Docker 部署。我们据此增加节点管理及平台对接，而不重新实现 Worker 间统计协议。[分布式运行](https://docs.locust.io/en/2.43.3/running-distributed.html)、[Docker 部署](https://docs.locust.io/en/2.43.3/running-in-docker.html)。

### 3.5 内网 / 公网兼容性（已确认：不依赖 VPN）

内网和公网节点使用同一套客户端及加密协议，只改变可访问的入口地址；不为两种网络开发两套压测引擎。公网接入不依赖 VPN，也不把 Locust 原始端口直接映射到公网。

| 通信链路 | 第一版设计 | 对外边界 |
| --- | --- | --- |
| 节点管理 | Agent 主动连接平台 HTTPS，领取任务包、续租并上报状态 | 建议复用平台 HTTPS 入口；节点无需入站端口 |
| 压测协调与统计 | Worker → 本节点私有监听端口 → 双向 TLS 连接 → 平台 TLS 接入组件 → 本轮 Master | 平台提供独立可配置的加密 TCP 入口，例如 9443；内部 RPC 不公开 |
| 被测请求 | Worker 直接连接管理员批准的被测目标 | 不经过 Django 或协调隧道，不自动暴露内网被测服务 |

- **传输实现**：优先以成熟的 stunnel 双向 TLS 封装原生 TCP，平台端和节点端组件随各自部署包交付，不自行编写加密协议或重写 Locust 通信。stunnel 支持客户端/服务端转接和证书校验；具体版本、打包方式和 Locust 长连接兼容性在首个原型中验证，不能把组件支持 TLS 当成整个平台已通过验收。[stunnel 官方说明](https://www.stunnel.org/howto.html)。
- **主动连接**：Agent 主动领取任务，节点 TLS 客户端主动连接平台入口；不要求平台反向访问节点、不要求节点固定公网地址或入站端口映射。平台侧必须有节点可访问的 HTTPS 和 TLS TCP 入口；若平台位于 NAT 后，需另外确认端口映射或受控接入部署，不承诺自动穿透任意防火墙。
- **地址分离**：分别配置节点可访问的 `platform_url`、TLS 协调入口和服务器证书名称；Master 内部监听地址与对外入口分开。不能用请求来源 IP、Docker 内部主机名、`0.0.0.0` 或平台本机 `localhost` 推导远端节点目标。本节点的私有 TLS 转接监听地址则由节点包明确生成给 Worker，不能与远端入口混淆。支持按节点指定内网入口，避免依赖 NAT 回环；证书必须匹配实际连接身份，不硬编码 NAS 地址。
- **入口与运行绑定**：首版不同运行全局排队，可以复用一个固定的 TLS TCP 入口，但只连接当前运行的 Master。只允许本次选定节点接入，并校验运行标识、节点与 Worker 的关联及脚本摘要，未完成握手不能发压。切换运行前关闭旧连接和旧运行准入；仅验证证书由同一个 CA 签发不等于获得任意运行权限。
- **三段预检**：分别诊断 Agent → 平台（DNS/TLS/注册）、Worker → Master（加密入口/证书/引擎握手）、Worker → 被测目标（地址/路由/连接）。只有心跳正常不能判定可压测；错误提示明确失败在哪一段。
- **目标可达性**：公网节点默认不能访问 `192.168.x.x` 等私有地址。仅内网可访问的目标应选择可达的内网节点；需要公网节点参与时，由管理员另行提供受控且可达的测试入口。不为满足节点接入需求而公开被测网站，也不默认通过平台代理被测请求或安装 VPN。
- **认证与证书**：管理通道严格验证 TLS，支持私有 CA；协调通道双向认证，每节点独立身份，支持吊销/轮换及到期提示。校验证书信任链和服务端名称，内网也不默认跳过。节点被吊销时应阻止新连接并终止其现有运行连接，不能只更新证书文件却保留旧连接。注册凭证与持久身份分离；SSH 密钥与业务凭证分开，不将私钥写入日志或镜像。
- **断线处理**：管理通信有限退避重连，任务继续使用幂等运行 ID；超过租约或本地最长运行时间则停止。TLS 连接重建不能触发重复压测，已结束运行不能被迟到指令重新启动。
- **混合运行的报告**：记录节点标签、网络接入方式和可选位置说明；区分节点异常与接口异常。跨网络响应时延包含链路时延，整体报告保留参与节点信息，不能把客户端时延直接解释成服务端处理时间。
- **仅 HTTPS/443 出网的边界**：TLS 封装的 Locust RPC 仍不是 HTTP。第一版允许独立加密 TCP 端口，不默认承诺只能经 HTTP 代理/CDN/443 的网络可用；改端口号不能解决协议限制。若实际部署存在该限制，再单独评估 WebSocket 隧道或支持四层转发的入口，不把这类网关扩展混入首版。

## 4. 节点安装与任务隔离

- 平台产生短期、一次性注册凭证和一个节点包的 Docker/Compose 安装说明，由管理员在设备执行一次。包内带齐 Agent、固定版本 Locust 及受支持依赖；已有 Docker 的设备可直接部署，无须另装 Worker。没有 Docker 的机器先由设备管理员安装，不在首版托管 SSH 密码或远程安装操作系统软件。
- Agent 长期身份与一次性注册凭证分离，可吊销；节点只能读自己被指派的运行数据，不能访问全平台配置、数据库或 Redis。
- 优先支持 Linux Docker 的 amd64/arm64 镜像，版本固定且运行前核验一致；原生 Python 客户端、Windows 服务打包放到后续阶段。
- 平台是任务包来源：冻结脚本、数据文件及校验摘要，Agent 接收后保存到本节点的 run_id/attempt_id 对应目录，启动 Worker 加载该目录中的脚本。Agent 不二次生成脚本，不把任务转派给其他节点。所有节点核对同一脚本版本后才允许发压；变量及测试数据分配另行按节点/虚拟用户区分。
- 首版统一通过 Agent 准备本地任务包，不同时引入 Worker 从 Master 动态下载脚本的另一套分发方式。下一次运行用新目录和新 Worker 进程，不在正在发压的进程中热替换脚本。
- 包内 Worker 子进程不通过参数、环境变量或任务文件接收 Agent 管理凭证；客户端详细设计仍需落实凭证文件访问权限。同一安装包、目录分离和普通子进程不等于不可信 Python 的安全沙箱。节点包不默认使用特权模式或挂载 Docker socket/无关宿主目录。
- 首版仅运行平台固定模板或管理员审核的可信 Locust 脚本。普通用户任意 Python、任意依赖在线安装不属于首版；若后续开放，先补任务容器/权限隔离验证。

### 后续 Linux 公钥 SSH 部署验收

- 用户在节点程序及镜像准备好后提供 Linux 机器地址、端口、用户名及现有密钥标识；使用已有公钥认证，不要求把私钥内容写入聊天、仓库或镜像。
- SSH 是部署和故障诊断通道，不是日常任务控制通道。节点安装完成后，SSH 会话断开不影响 Agent 常驻运行。
- 先只读核对机器身份、系统/CPU 架构、Docker 状态、磁盘资源、已有服务和三段网络连通性；确认具体安装目录、容器名、端口及资源限制后再部署，保留已有容器和业务数据。
- 需要新开公网端口、调整防火墙、修改宿主路由或扩大系统权限时，先说明精确变更和回退方式并确认，不把公钥 SSH 授权当作无限制设备管理授权。按已选方案不安装 VPN。
- 验收覆盖登记、重启、领取脚本、低负载受控运行、报告回传、停止、失联和重连。是否重启 Docker 守护进程或影响其他服务需另行确认；回退以停止/移除本次节点容器和恢复其配置为限。

## 5. 一次压测的流程

1. 用户选择计划、脚本、目标、变量及节点，平台冻结本次运行快照。
2. 平台启动本次 Master 和对应 TLS 接入，向所选 Agent 提供脚本包、运行标识及加密协调入口；原始 Master 地址不直接暴露给远端网络。
3. Agent 校验任务包、准备目录和本地 TLS 转接，启动 Worker 加载本地脚本；文件、版本或加密连接检查失败时不上报准备成功。
4. Worker 连接 Master；平台确认所选节点准备成功，Master 确认预期 Worker 已就绪后才开始发压。Agent 在线不能直接满足这一条件。
5. 平台把总用户数、启动速率、持续时间等目标参数交给 Master，由 Master 统一分配并驱动 Worker 执行。
6. 请求结果经 Worker → Master → 平台展示；机器及进程健康信息由 Agent 另行上报，二者不混算。
7. Master 正常停止并提交尾部统计，Agent 回收本次 Worker 进程，平台生成报告；异常结束明确保留原因及统计缺口。

正式压力运行前必须先做单用户短时验证。验证也使用上述同一执行链路，只是负载参数更小；每次执行都冻结自己的快照，不另开发一套调试执行器。

- 首版参数以虚拟用户数、用户启动速率、持续时间、用户等待时间为主。用户数不是每秒请求数；页面必须区分并发用户、接口 RPS 与完成业务循环的 TPS，不能保证指定并发一定达到某个 RPS。
- 一个压测运行独占所选节点槽位；首版压测运行全局排队，不做多项目同时争抢节点及弹性扩缩容。
- 先全部准备再启动；版本不一致、节点不足、脚本错误或目标不可达明确终止，不能悄悄少用节点继续并标记正常。Master 接入的 Worker 必须能关联到本次选定的节点/运行，不能仅凭连接数量接收其他运行的 Worker。
- 状态建议为排队、准备中、运行中、停止中、已完成、失败、已取消、结果不完整。「请求出现失败」与「压测进程失败」分开；阈值决定测试结论，运行状态决定这份结果是否完整。
- 命令带 run_id、attempt_id 和幂等 ID，重复投递不重复发压。启动后 Agent 重启、Master 丢失或通信异常，不自动重放整次业务请求；先终止孤儿进程并确认状态，再由用户创建新运行。
- 所有执行器有本地最大时长和可过期租约。平台失联或心跳续租失败超过约定时间必须停止；不能只依赖平台发出一次「停止」命令。界面停止先显示「停止中」，收到确认或确定已超时终止后再改终态。

## 6. 统计、报告及保护

- Worker 统计由 Master 汇总，再由适配器按批次发送平台；建议首版每 5 秒上报一批，节点 CPU/内存等资源数据单独上报。
- 按固定的接口/事务名称分组，动态 URL 中的 ID 不变成无限多个指标项。只保留有限错误样本，不逐条把全部请求/响应写入 MySQL 或推送浏览器。
- 平台保存带运行 ID、采样序号和时间范围的统计记录，重复上报幂等覆盖，不把累计快照再次相加。P95/P99 采用 Master 汇总统计，不对各节点百分位做平均。
- 报告区分全程与采样窗口统计，展示用户数、RPS、响应时延、P95/P99、错误率、接口明细、节点资源、开始结束时间和中止原因。Master/Worker 缺失尾部统计时标记不完整，不能填零或算作通过。
- 引擎提供事件扩展及统计导出，可作为适配基础；不依赖抓取 Locust 网页文字。长压测与 gevent 环境在独立进程运行，避免在 Django/Celery 导入压测环境改变主服务行为。[事件扩展](https://docs.locust.io/en/2.43.3/extending-locust.html)、[统计导出](https://docs.locust.io/en/2.43.3/retrieving-stats.html)、[库模式及进程说明](https://docs.locust.io/en/2.43.3/use-as-lib.html)。
- 仅能压测管理员批准的目标；目标地址、重定向范围、并发上限、最长运行时间和停止权限服务端校验。控制通道独立做身份认证，不继承 API 业务请求的跳过 TLS 校验行为。
- 必须同时监测发压节点资源，否则节点 CPU/网络饱和会被误判成被测网站性能差；仅凭客户端统计不能断言数据库/服务器瓶颈，需要服务端监控才能归因。[请求速率排查](https://docs.locust.io/en/2.43.3/increasing-request-rate.html)。

## 7. 与现有 API / AI 功能的关系

- API 用例可作为以后创建压测脚本的来源，但先生成独立快照，不直接高并发重复执行现有 requests 调试器。
- 可复用请求结构、变量提取和业务步骤；必须重新明确每个虚拟用户的登录会话、数据分配、用户等待时间、事务统计和业务失败判断，并通过 Locust 客户端计量请求。
- 创建、删除、权限变更等有副作用的 API 场景不可默认整套循环压测；需确认目标环境、独立测试账号及数据策略。
- AI 用于生成/解释脚本和报告建议；脚本先经低负载验证，再交付固定压测引擎执行。运行中不由 AI 随意改变压力、目标或断言。

## 8. 分阶段交付建议

1. **单节点闭环**：平台端内置独立 Master，部署一个包含 Agent + Worker 的节点包；节点登记/心跳、脚本包接收、单用户验证、启动/停止、基础实时指标、执行记录与结果摘要。HTTPS 管理、双向 TLS 协调、租约、资源上限、准备检查和停止机制从第一阶段做起；先验证本地链路，再用用户提供的 Linux 机器做无 VPN 跨网验证。不先做 LocalRunner 再重写成 Master/Worker。
2. **多节点与报告完善**：沿用相同包及协议扩展到两个以上节点，补齐数据分片、跨节点准备屏障、故障回收及完整报告。请求调度与统计合并继续使用同一 Master，不新建平台分布式调度器。
3. **产品增强**：从 API 场景派生、AI 辅助生成、阶梯负载、性能阈值、报告对比、计划任务及邮件。复用平台 UI/权限/通知，不把旧 API/UI 的生成状态机混进来。

验收不能只看「有曲线」：必须覆盖一份节点包完整安装、平台脚本包与 Worker 实际加载文件一致、不同运行不串脚本、Agent 在线但 Worker 未就绪不能发压、运行节点匹配、受控目标上请求数核对且统计不重复累加、命令重复投递、停止后不再新增请求、失联自动停止、节点宕机/重连、尾部统计缺失、目标限制和越权、节点资源饱和、停止失败提示。

网络验收增加内网单节点、无 VPN 的公网节点接入、内外网混合节点、入口地址错误、证书错误/过期/吊销、非本次选定节点接入、旧运行连接跨轮残留、平台可达但 Master 不通、协调连接正常但目标不可达、短暂断网重连及平台失联自动停止。确认平台原始 RPC 未对公网开放、节点无需入站端口。不以同一内网模拟测试代替真实跨网验收；公网接入未验证时不得交付为已支持。实际压测目标及最大负载在执行验证前单独确认；本轮不运行任何压力测试。

## 9. 已确认与实施前细化

- **已确认**：两种部署包；节点包包含 Agent 和 Worker；Agent 接收脚本并启动 Worker；Master 负责压力控制及统计；节点同仓开发、后续通过用户提供的公钥 SSH 安装调试；兼容内网、公网机器和混合部署，不依赖 VPN，公网连接必须加密。不再把内部职责当作多套用户系统。
- **部署前确认**：平台对外可达地址、HTTPS 与 TLS TCP 端口、证书签发方式及被测目标可达范围。在明确机器和入口前不修改防火墙、不暴露内部 RPC。TLS 组件随平台包/节点包交付，不要求用户额外部署 VPN。
- **需要细化而非重选架构**：第一期页面及接口、任务包结构、进程/凭证权限、启动握手、租约与停机超时、资源限制及统计适配契约。首次实现前形成可执行任务和验收标准。
- 首批节点系统、CPU 架构及 Docker 是否可用，在客户端打包阶段盘点；目前无远程目标信息，本轮只补设计，不访问或修改节点设备、不启动压测，也不更改现有 UI/API 执行逻辑。
