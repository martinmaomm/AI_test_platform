## 1. 目标与范围

确认 API 自动化可以稳定完成：

`Swagger / 网页探索 → 工作区生成 → 实际验证 / 人工修改 / AI 修复 → 保存 → 单用例 / 套件 / 计划任务 → 报告与邮件`

本轮主要验收 API 自动化。UI 自动化只做共享功能冒烟，不重新探索全部 UI 业务；知识库只检查基本访问，不重新生成手工用例或向量索引。不新增功能、不做压力测试，不把测试站或模型服务商本身的缺陷算作平台缺陷。

重要区别：

- **平台正确性**：步骤、变量、断言、执行状态、保存和权限符合规则。这是本轮必须守住的底线。
- **AI 生成质量**：目标是否覆盖、定位与提取是否合理、人工需要改多少。单独记录，不能用“人工改完通过”冒充“AI 自动生成通过”。
- **真实运行通过**：必须有对应版本、实际请求、结果和断言证据；模拟通过、生成完成、HTTP 200 都不能单独证明业务通过。

### 当前契约（不是本计划提出的新功能）

- 结构化配置是执行源；Python 仅查看、复制、导出，平台与导出共用 requests 运行核心。
- 端点模式固定一个被测目标，登录、准备和清理属于辅助范围；多步骤仍可保存为端点用例。
- 场景、套件内用例顺序执行，独立用例不隐式共享提取变量或登录会话。当前单个 solo worker 不等于多 worker 下也有全局串行保证。
- 每次最多选择 50 个接口、最多规划 20 个场景；候选最多 3 轮尝试，规划结构错误沿用现有一次修正预算。
- API 变量覆盖顺序为：本次执行 > 套件 > 用例 > API 环境默认值。
- 修改后的草稿不能沿用旧的通过状态；采用候选、保存、重新验证是不同动作。
- API 业务请求跳过 TLS 服务器证书校验，仅限可信测试环境；不能影响模型、SMTP 等其他 HTTPS/TLS 连接。
- 普通手动用例/套件执行不自动发邮件；计划任务定时触发或“立即执行”才按通知配置发送。

## 2. 三批执行顺序与停点

| 顺序 | 做什么 | 模型 / 外部写入 | 完成条件 |
| --- | --- | --- | --- |
| 准备检查 | 确认代码、既有证据、测试脚本、环境和数据边界 | 只读；不启动真实任务 | PRE 项完成，未确认项明确记录 |
| 第一批：隔离功能回归 | 覆盖下方功能清单，修正已确认失效的测试替身/定位器后再复跑 | 模拟模型、临时 SQLite、业务 HTTP 替身或本机夹具；不访问 NAS 业务接口 | 核心功能和保护契约通过；测试基础设施失败与产品失败已区分 |
| 第二批：小样本真实联调 | 按第 5 节执行 3 个代表性生成任务；随后独立重跑、套件、导出、计划与邮件验收 | 真实模型、Redis/worker、专用测试站和指定收件人；须先落实授权和参数 | 真实闭环有证据，重跑不借用上次状态，费用与人工介入已记录 |
| 第三批：异常与最终复核 | 补异常注入、权限/误操作保护、修复后回归及 UI 共享功能冒烟 | 默认隔离；真实服务停机、全局配置切换等不作为默认动作 | 达到第 7 节放行标准，形成结论与剩余问题清单 |

三批是执行顺序，不是要求每个检查项都重新调用模型。已有结果只有在代码版本、配置、测试范围和证据均匹配时才复用；相关实现变化、原测试失败或存在明确疑点时才补跑。

## 3. 数据、授权与执行规则

1. 真实写操作只在已获授权的测试环境进行。优先独立验收项目和专用账号；不得修改登录账号、其共享角色、既有业务数据或其他项目数据。
2. 本轮新建对象使用运行时唯一名称，登记名称、ID、所属运行；编辑和删除前核对为本轮对象。重复执行必须产生新值，不能把探索阶段或提示词里的时间戳写死。
3. 默认不清库、不批量删除历史用例、不修改全局模型/SMTP配置。收尾只清理本轮登记的资源；无法确认归属则保留并报告。需要新增操作范围时再确认，不重复索取已有同范围授权。
4. 取消、超时、断电或请求失联不保证回滚或清理。对“请求可能已生效”的情况先查询真实状态，不能盲目重放新增、改密、授权或删除。
5. 权限保护采用隔离夹具：受保护账号、共享角色、本轮临时账号/角色、其他资源同值 ID、改名字段和不含业务关键词的路径。不得拿真实登录账号实际变更权限来证明保护有效。
6. `account_safety` 是显式声明驱动的保护，不是任意 API 的自动安全沙箱。真实账号/角色场景执行前必须审阅声明及请求目标；声明缺失或含糊时，不允许无人审阅自动执行相关敏感步骤。
7. 第一批不消耗真实模型额度。第二批每个代表性生成任务先完整发起一次；用既有候选定向修复，不反复全量生成。达到冻结的轮次、工具或时间预算后记录终态，不自动加大限制。
8. 真实模型调用记录任务、调用阶段、耗时、尝试次数及供应商可提供的 token/费用；不可获取时记“不可用”，不是 0。不得绕过平台限制，或悄悄替换成更贵模型。
9. 邮件仅向已确认的测试收件人发送。不停整个共享 worker 来制造失败；异常优先注入到隔离环境。若需要真实重启，先确认无在途任务及影响范围，结束后验证服务恢复。
10. 发现误改权限、越界请求、脚本丢失、错误显示通过或副作用不明，立即停止对应真实链路，保存证据并调查。不能用无限重试掩盖。

## 5. 第二批真实联调样本

真实执行前填写第 2 节参数；本计划中的目标描述是建议样本，不是立即执行指令。三个生成任务共用同一已确认模型，若服务商故障，先记阻塞，不把换模型当作同一次成功结果。

| 样本 | 建议目标与最小范围 | 必须保留的证据与验收 |
| --- | --- | --- |
| LIVE-A：端点模式 | 一个需要登录的查询接口；只要求生成 1 个正向端点用例，辅助范围仅含实际需要的登录/准备/清理接口 | 从页面真实登录平台、选目标、确认生成；worker 接收并完成；保存仍为端点类型；保留完整步骤并重开编辑 |
| LIVE-B：Swagger 场景 | 一个普通业务对象的新增→精确查询→编辑→删除→验证不存在；另一个明确不登录/错误参数的反向场景，共 2 个独立场景 | 区分 HTTP 与业务码；反向场景不能改成正向来通过；展示场景独立、失败处理、人工修改及重新验证，不涉及共享角色改权 |
| LIVE-C：网页来源 | 同一可信站点的一个小模块，探索一个必要业务流程，API origin 留空；仅选择所需样本生成 1 个场景 | 有真实 MCP 轨迹与网络样本；自动识别/确认来源；交接后重新取得认证与动态 ID，不使用探索遗留数据；证据不足则如实记录，不用 Swagger 暗中替代 |

每个最终验收候选须先人工核对目标和断言，再满足以下要求：

- 保存后**连续独立运行 3 次**，无中途修改脚本、无前一轮会话或 token/ID 注入，3 次均通过。脚本有修改则重新开始这组计数，保留之前失败记录。
- 断言能验证该场景目标：CRUD 必须包含业务结果断言，不能仅凭 HTTP 状态码通过；专门验证未认证返回 HTTP 401 的反向场景，可以把该状态码作为核心断言。删除后用详情读回或已证明完整的查询范围验证，不以第一页为空冒充删除成功。

然后用这些已保存用例完成一组跨功能联调即可，不要求每个候选重复创建套件、计划或发送邮件：

- 将至少两个独立正式用例组成套件，核对顺序、变量覆盖和成员报告；故意失败后继续的契约先用隔离夹具测试，真实业务不必为了失败而破坏数据。
- 至少选一个多步骤候选导出 Python，在仅具备导出说明所需依赖、不可导入平台后端包的环境运行；使用本轮新数据，核对平台与导出的一致性。
- 使用这些已保存用例创建一个验收计划：验证一次“立即执行”和一次到点触发；避免与旧任务重叠。发送到已确认邮箱，并由实际收信证明送达，收尾暂停/删除本轮验收计划。
- 执行前后读回测试账号身份/权限和本轮资源状态。任何遗留数据必须列清单，不能用“脚本通过”代替清理核实。

### AI 质量单独评分

每个任务记录：初次自动通过 / 平台有限修复后通过 / 人工修改后通过 / 失败或阻塞，以及人工改动的原因和范围。

三个样本量不足以推算总体成功率。人工少量修正提取路径或断言类型可接受，但必须标注；如果所有样本都需要重写登录依赖或主体业务流程，则生成能力不能判为收尾完成，需要先处理共性原因。

### 通用性补充

不要求为本轮另搭一整套大型网站，但至少用一个**不同字段命名、路径、响应包裹结构和认证方式的受控夹具**覆盖生成与执行契约，确认没有依赖商城关键词。声明和运行器的离线通用性通过，不等于真实模型已在第二个网站验证过；真实第二站可在明确环境后作为扩展项，不冒充当前覆盖。

## 7. 放行标准与缺陷处理

### 第一批进入真实联调的门槛

- 隔离测试不会连接业务数据库/外部服务；已知测试替身/定位失配有明确处理结果。
- P0 中与生成、执行、保存、变量、权限及账号保护相关的隔离检查通过，无未解释失败。
- 真实站点、专用账号、请求范围、模型和预算已落实；当前 worker/Beat 状态可确认。

### API 模块收尾、进入下一个模块的门槛

1. **本轮适用 P0 全部通过**；P1 中阻断生成、保存、执行、报告/计划/通知正式闭环的问题解决。未完成的真实项目不能被模拟结果替代。
2. LIVE-A/B/C 完成真实来源到正式用例的闭环；每个纳入验收的最终候选满足独立 3 连跑，至少一个通过独立 Python 执行，套件及实际 Beat/邮件链路有证据。
3. 无误改登录账号/共享角色、无跨项目数据泄露/修改、无静默丢脚本、无把失败/未知/全跳过显示为通过；发生过的此类缺陷必须修复并定向回归。
4. AI 自动通过与人工修正通过分开报告；没有“每个简单样本都必须重写主体流程”的共性质量问题。
5. 异常可定位、已有执行证据可恢复；未清理资源、通知失败、模型/站点限制和其他遗留问题逐项登记。
6. UI 共享功能冒烟通过；代码/测试变更完成审查与相关复测；只在确有运行代码变更且任务空闲时重启必要服务。

结论只选以下三种之一：

- **通过**：上述门槛满足，仅可保留不阻断操作的体验问题，附后续处理清单。
- **有条件通过**：例如真实邮箱/第二来源尚不可用，明确未验证功能与影响，并由用户接受后决定是否先开发其他模块；不得称为 API 全量验收通过。
- **不通过**：核心闭环或数据边界存在阻断问题；先修复再决定，不扩大模块开发范围掩盖问题。

缺陷严重度：S0 为越权、误改重要数据、严重数据丢失等，立即停止对应真实执行；S1 为主流程不可完成、错误显示通过、结果不可追溯等，阻断放行；S2 为有明确绕行的非核心问题；S3 为文案/样式体验。根据实际影响分级，不因“测试环境”就降低安全或数据问题等级。

若后续只授权测试与分析，发现产品问题先报告，不自动修复业务代码。获得修复授权后按根因最小改动、中文提交，并复跑失败项及直接受影响链路，不重跑所有付费生成。
