# Swagger 响应规范参考设计

## 背景

场景步骤编辑器当前把端点保存的 `responses` 原始 JSON 直接展示在 Monaco 编辑器中。对于 Swagger 2.0 响应使用 `$ref` 的情况，页面只能显示引用路径，无法像 Swagger UI 一样展示状态码、描述、响应内容类型和可读的响应模型/示例。

## 目标

在不改变现有端点接口返回主体结构的前提下，让场景步骤编辑器的“响应规范参考”能够：

1. 按响应状态码展示响应定义，并保留接口文档中的顺序。
2. 展示状态码描述，例如 `200 / OK`、`401 / Unauthorized`。
3. 解析 Swagger 2.0 `#/definitions/...` 和 OpenAPI 3 `#/components/schemas/...` 引用。
4. 对有响应体的状态码展示响应内容类型、Example Value 和 Model；没有响应体的状态码只展示描述。
5. 继续兼容没有模型定义、旧格式响应以及现有端点缓存数据。

## 方案

### 后端

在 API 端点列表和详情返回的每个端点对象中新增 `response_definitions` 字段，仅携带当前规范的 `definitions` 与 `components.schemas`。不改变端点列表仍为数组的既有契约，也不覆盖原始 `responses` 数据。

### 前端

场景编排器将 `responses` 与 `response_definitions` 一起传给步骤编辑器。步骤编辑器负责：

- 兼容旧的纯 `responses` 入参和新的包装对象；
- 解析响应媒体类型、示例和 `$ref`；
- 从解析后的 schema 生成缺少显式 example 时的示例值；
- 以状态码卡片列表替换单个原始 JSON 编辑器，使用固定高度的只读 JSON 编辑器避免响应内容撑破布局。

## 边界与取舍

- 本次只改场景步骤编辑器中的响应参考，不改真实接口调试响应，也不改变执行器断言逻辑。
- 后端会在每个端点附带当前规范的模型定义，数据存在重复，但实现简单、兼容性好，且避免改变已有列表响应结构；后续若规范体积很大，再考虑按规范单独缓存模型定义。
- 没有定义或无法解析的 `$ref` 保留原始 schema 展示，不阻断编辑和调试。

## 验收标准

- 以截图中的注册接口为例，`200` 能显示解析后的 `code/data/message` 模型示例，`201/401/403/404` 能显示各自描述。
- 页面不再只显示 `$ref` 原始 JSON。
- 老端点没有 `response_definitions` 时仍能打开参考面板。
- 后端 Python 检查、前端 lint/build 或等价静态校验通过。
