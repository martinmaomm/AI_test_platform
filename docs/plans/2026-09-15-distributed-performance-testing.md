# 分布式性能测试架构草案

状态：架构待确认，尚未开始性能模块开发。已确认的部署边界：首版节点在同一内网或通过 VPN 互通。

本轮仅修改首页：App 自动化入口改为「安全测试（开发中）」，描述为「检测应用安全风险与常见漏洞，提供修复建议。」；性能测试、安全测试均继续置灰且不可点击。不删除旧 App 业务代码、不部署客户端、不向被测网站发起压测。

## 1. 现状与目标

- 当前性能工作区是占位页面，后端尚无节点注册、压测调度、统计汇总业务。`backend/requirements.txt` 已声明 `locust==2.43.3`，但有依赖不等于已集成。
- 目标是平台管理测试计划、节点、运行及报告；节点实际发压，不让请求流量经过 Django。
- UI/API 自动化继续沿用原流程，性能模块独立执行。既有全局串行偏好建议解释为「不同压测运行排队」；同一次压测必须允许多个虚拟用户并发，各用户内部业务步骤可按顺序执行。

## 2. 路线比较

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 平台简单接入 Locust，节点手动启停 | 快速验证引擎和压测脚本 | 节点运维、项目权限、历史报告体验分散，不满足完整中控需求 |
| 平台 + 轻量节点 Agent + Locust 引擎（推荐） | 自己控制产品体验，复用成熟的用户调度、分布式通信及统计 | 仍需实现节点生命周期、任务一致性、异常恢复与平台报告 |
| 整套自研请求与分布式引擎 | 完全自由 | 需要自行处理并发、限流、连接复用、统计合并，维护与验证成本最高 |

建议用第二种。不是修改 Locust 源码，也不是把它的网页嵌入平台；开发薄适配层并固定运行时版本。首版以项目现有版本作为候选基线，客户端镜像还需单独验证，不能直接复用平台整个 venv。

## 3. 职责与连接

1. **平台控制端（现有 Django/Vue）**：项目权限、节点登记、计划及脚本快照、执行变量、启动/停止命令、状态与报告。Celery 可做短时间派发/核对工作，不把一次长压测占在现有 solo Worker 中，也不把异地节点接入平台 Redis 当 Celery Worker。
2. **节点 Agent（需要开发）**：机器身份、心跳、容量和版本上报、领取命令、校验任务包、管理任务进程/容器、上传结果及有限日志。它不是 LLM 智能体，不在发压循环里调用模型。
3. **Locust Master（每次运行隔离实例）**：运行在专用执行/协调服务中，而非 Django 进程；控制 Worker 用户数量、爬升及停止，汇总请求统计。首版可与平台同机但使用独立服务及资源限制，后续再拆机。
4. **Locust Worker**：在所选节点上执行虚拟用户，向目标接口发请求；一个物理节点可预留多个 Worker 槽位，但总量受 CPU/内存限制，不默认用满机器。

连接分两条：

- **管理通道**：Agent 主动连接平台的认证 HTTPS 接口领取命令、上报心跳/结果，可先用长轮询；不要求平台能够 SSH 到每台节点。
- **压测通道**：Worker 通过内网/VPN 连接 Master 的 Locust RPC 端口（默认 TCP 5557），并能访问被测网站。平台可达不等于 Master 或被测系统可达，启动前分别检查。该端口仅受信网络可用，不直接暴露公网。

Locust 原生 Master 负责控制和收集 Worker 统计，自身不发压；官方支持 Docker 部署。我们据此增加节点管理及平台对接，而不重新实现 Worker 间统计协议。[分布式运行](https://docs.locust.io/en/2.43.3/running-distributed.html)、[Docker 部署](https://docs.locust.io/en/2.43.3/running-in-docker.html)。

## 4. 节点安装与任务隔离

- 平台产生短期、一次性注册凭证和 Docker/Compose 安装说明，由管理员在设备执行一次；已有 Docker 的设备可直接部署。没有 Docker 的机器先由设备管理员安装，不在首版托管 SSH 密码或远程安装操作系统软件。
- Agent 长期身份与一次性注册凭证分离，可吊销；节点只能读自己被指派的运行数据，不能访问全平台配置、数据库或 Redis。
- 优先支持 Linux Docker 的 amd64/arm64 镜像，版本固定且运行前核验一致；原生 Python 客户端、Windows 服务打包放到后续阶段。
- 任务包冻结脚本、数据文件及校验摘要；所有节点核对同一版本后才启动。变量按任务下发，测试账号按节点/虚拟用户分片，不能让所有并发用户覆盖同一条业务数据。
- 执行器不继承 Agent 的管理凭证，不给任务容器 Docker socket、宿主目录或特权权限；Agent 与运行脚本的信任边界需在客户端详细设计中落实。进程隔离不是任意 Python 代码的安全沙箱。
- 首版仅运行平台固定模板或管理员审核的可信 Locust 脚本。普通用户任意 Python、任意依赖在线安装不属于首版；若后续开放，先补任务容器/权限隔离验证。

## 5. 一次压测的流程

创建计划 → 选择脚本/目标、变量和节点 → 单用户短时验证 → 冻结本次配置 → 节点准备 → 全部就绪后爬升 → 持续压测 → 停止及收集尾部结果 → 平台报告。

- 首版参数以虚拟用户数、用户启动速率、持续时间、用户等待时间为主。用户数不是每秒请求数；页面必须区分并发用户、接口 RPS 与完成业务循环的 TPS，不能保证指定并发一定达到某个 RPS。
- 一个压测运行独占所选节点槽位；首版压测运行全局排队，不做多项目同时争抢节点及弹性扩缩容。
- 先全部准备再启动；版本不一致、节点不足、脚本错误或目标不可达明确终止，不能悄悄少用节点继续并标记正常。
- 状态建议为排队、准备中、运行中、停止中、已完成、失败、已取消、结果不完整。「请求出现失败」与「压测进程失败」分开；阈值决定测试结论，运行状态决定这份结果是否完整。
- 命令带 run_id、attempt_id 和幂等 ID，重复投递不重复发压。启动后 Agent 重启、Master 丢失或通信异常，不自动重放整次业务请求；先终止孤儿进程并确认状态，再由用户创建新运行。
- 所有执行器有本地最大时长和可过期租约。平台失联或心跳续租失败超过约定时间必须停止；不能只依赖平台发出一次「停止」命令。界面停止先显示「停止中」，收到确认或确定已超时终止后再改终态。

## 6. 统计、报告及保护

- Worker 统计由 Master 汇总，再由适配器按批次发送平台；建议首版每 5 秒上报一批，节点 CPU/内存等资源数据单独上报。
- 按固定的接口/事务名称分组，动态 URL 中的 ID 不变成无限多个指标项。只保留有限错误样本，不逐条把全部请求/响应写入 MySQL 或推送浏览器。
- 平台保存带运行 ID、采样序号和时间范围的统计记录，重复上报幂等覆盖，不把累计快照再次相加。P95/P99 采用 Master 汇总统计，不对各节点百分位做平均。
- 报告区分全程与采样窗口统计，展示用户数、RPS、响应时延、P95/P99、错误率、接口明细、节点资源、开始结束时间和中止原因。Master/Worker 缺失尾部统计时标记不完整，不能填零或算作通过。
- 引擎提供事件扩展及统计导出，可作为适配基础；不依赖抓取 Locust 网页文字。长压测与 gevent 环境在独立进程运行，避免在 Django/Celery 导入压测环境改变主服务行为。[事件扩展](https://docs.locust.io/en/2.43.3/extending-locust.html)、[统计导出](https://docs.locust.io/en/2.43.3/retrieving-stats.html)、[库模式及进程说明](https://docs.locust.io/en/2.43.3/use-as-lib.html)。
- 仅能压测管理员批准的目标；目标地址、重定向范围、并发上限、最长运行时间和停止权限服务端校验。控制通道独立做身份认证，不继承 API 业务请求的跳过 TLS 校验行为。
- 必须同时监测发压节点资源，否则节点 CPU/网络饱和会被误判成被测网站性能差；仅凭客户端统计不能断言数据库/服务器瓶颈，需要服务端监控才能归因。[请求速率排查](https://docs.locust.io/en/2.43.3/increasing-request-rate.html)。

## 7. 与现有 API / AI 功能的关系

- API 用例可作为以后创建压测脚本的来源，但先生成独立快照，不直接高并发重复执行现有 requests 调试器。
- 可复用请求结构、变量提取和业务步骤；必须重新明确每个虚拟用户的登录会话、数据分配、用户等待时间、事务统计和业务失败判断，并通过 Locust 客户端计量请求。
- 创建、删除、权限变更等有副作用的 API 场景不可默认整套循环压测；需确认目标环境、独立测试账号及数据策略。
- AI 用于生成/解释脚本和报告建议；脚本先经低负载验证，再交付固定压测引擎执行。运行中不由 AI 随意改变压力、目标或断言。

## 8. 建议分阶段交付

1. **最小闭环**：单节点 Agent + 独立 Locust 执行器；登记/心跳、手动选择可信 HTTP 脚本、启动/停止、基础实时指标、执行记录与结果摘要。节点租约、资源上限和停止机制从第一阶段做起。
2. **分布式与可靠性**：两个及以上 Worker 节点、Master 汇总、数据分片、准备屏障、故障回收、完整平台报告。第一阶段仍沿用相同 Agent/Run 协议，避免单节点方案另起一套。
3. **产品增强**：从 API 场景派生、AI 辅助生成、阶梯负载、性能阈值、报告对比、计划任务及邮件。复用平台 UI/权限/通知，不把旧 API/UI 的生成状态机混进来。

验收不能只看「有曲线」：必须覆盖受控目标上请求数核对、命令重复投递、停止后不再新增请求、失联自动停止、节点宕机/重连、尾部统计缺失、目标限制和越权、节点资源饱和、停止失败提示。实际压测目标及最大负载在执行验证前单独确认；本轮不运行任何压力测试。
