# 服务管理器“未纳管”修复验收

## 根因与修改

此前后端、Celery、性能控制器和 Caddy 仍在运行、健康检查正常，但管理器记录的进程启动时间与新的 Python 进程读取值相差 1 秒。原实现用 `psutil.Process.create_time()` 与持久化时间作 20 毫秒容差比较，误判身份失效后清除了 PID；重新启动又被已有进程冲突检查拒绝，最终显示“未纳管”。

本机固定依赖 psutil 7.2.2。检查其源码可见，macOS 的公开 `create_time()` 会通过 `adjust_proc_create_time()` 根据模块初始系统启动时间与当前值作校准；其自身防 PID 复用检查使用 `_get_ident()` 中未经该校准的内核启动标记。不同解释器的初始化基准和后续系统时间变化使普通时间不适合充当持久化进程身份。

- 管理器及服务统一采用 PID、原始内核启动标记、本次系统启动 ID、psutil 版本组成的精确身份；保留完整启动命令指纹及工作目录检查。
- 系统启动 ID 在 macOS 读取 `kern.bootsessionuuid`，Linux 读取 `/proc/sys/kernel/random/boot_id`，防止机器重启后重新出现相同 PID/启动偏移时被错误接管。
- 不再放宽时间容差。相同命令和目录、启动标记仅差 1 毫秒也拒绝接管或停止。
- 私有 psutil 调用集中在单一适配函数中，依赖仍固定为 7.2.2。依赖升级需受控重启及身份回归，不跨版本解释已存身份。
- 状态格式升级到 v2。v1 普通启动时间不转换为所有权；已存在的手动服务仍只报告冲突，不自动接管或强制终止。

## 隔离验证

```bash
backend/.venv/bin/python -m unittest discover -s backend/scripts -p 'test_platform_service*.py' -v
```

35 项测试通过，全部使用本地临时目录和测试子进程，不连接现场数据库、队列或业务目标。

新增回归覆盖：

- 模拟普通启动时间前后偏移 1 秒及 1 小时，真实测试子进程仍保持纳管；继任管理器从磁盘恢复身份后启动幂等、可正常停止。
- 在新的 Python 解释器中模拟不同的时间校准结果，读取同一子进程仍获得相同稳定身份。
- 模拟 PID 复用、本次系统启动 ID 变化、依赖版本变化，拒绝接管、重复启动和误停同命令进程。
- v1 旧状态不授予所有权，外部进程保持存活。
- 管理器自身身份核验不受普通时间偏移影响，命令或原始启动标记不符仍拒绝。
- 时钟调整期间测试子进程意外退出，原有退避流程能重新启动服务。

既有单服务重启、停止顺序、重试上限、手动重置、外部服务与端口冲突、停止超时、配置刷新、客户端断连及健康探针测试同时通过。

## 现场生效

切换前及停止前分别确认活动压测为 0，Celery 的 active/reserved/scheduled 均为空。逐项核对 PID、稳定身份、完整命令和工作目录后，先停止旧管理器，再优雅停止控制器、Celery、Caddy 和后端；没有使用强制终止。旧状态和脚本备份保留在 Git 忽略的 `backend/temp/platform-services/identity-repair-backup/` 中。

通过 `./platform start` 启动新管理器，并用独立解释器验证磁盘记录及实际进程身份一致：

| 进程 | PID | 验证结果 |

| 管理器 | 1667 | v2 身份有效，管理接口响应正常 |
| 后端 | 1669 | 已纳管，HTTP API 响应正常 |
| Celery | 1670 | 已纳管，1 个 Worker 响应心跳 |
| 性能控制器 | 1671 | 已纳管，数据库连接及心跳有效 |

四项服务均为 `running`、`healthy=true`、重试计数 0。再次执行 `./platform start` 均返回“已在运行”，PID 未变，没有重复服务。

启动约 174 秒后再次用独立解释器检查：管理器及四项服务身份仍有效，PID 未变，每项仅有一个匹配进程，重试计数仍为 0，CLI 健康检查全部通过。16:55:03（北京时间）读取数据库时，控制器在线、心跳距当前 0.46 秒；`osjp3.1` 节点在线、版本 0.3.1，心跳距当前 1.93 秒。

## 验证边界与回退

未修改现场系统时间、未故意中断数据库或现场服务来触发故障，也未对业务目标发压；时钟偏移和意外退出通过隔离故障注入验证。现场验证为当前 macOS 环境，Linux 未作实机验收。

未更改节点镜像、固定模板、数据库结构、计划或运行记录。管理器仍不提供开机自启，进程异常退出仍遵守 10 分钟内最多 5 次的恢复上限。

其他机器升级时，应先在旧版本下确认任务空闲并停止服务/管理器，再启动新版本。已丢失所有权的旧进程需要逐项核实后优雅退出。若需回退本次代码，也应先用新版本停止其服务与管理器，再恢复旧脚本并启动；不要把任一版本的旧状态覆盖到仍运行的另一版本管理器上。
