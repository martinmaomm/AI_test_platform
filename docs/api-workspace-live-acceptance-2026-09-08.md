## 完整范围试运行的发现

工作区 24 首次规划返回 31 个场景，超出 20 个上限；一次纠错仍原样返回，尚未发出目标业务请求。增强规划/纠错指令后重新生成了 15 个场景，顺序运行完毕。

本轮结束时系统记录为 **5 passed、2 failed、8 needs_review**。其中子场景 32 的 passed 在人工复核中被判为无效，不能计入验收通过：

1. **操作对象错误（子场景 32）**：创建菜单未返回新 ID。模型修复时改为从未限定的菜单树取 `body.data[0].id`，更新了已有菜单 ID 1。状态码与弱身份断言均通过，但不满足“只操作本轮新建数据”。
   - 已使用该次修改前保存的菜单树响应恢复 ID 1；恢复前先确认当前值仍与错误执行后的快照一致，恢复后逐字段读回确认。
   - 已通过标准草稿 PATCH 加入本轮唯一名称的 `eq` 身份核对，将原通过证据置为 `stale`；未再运行此草稿，也未保存成正式用例。
   - **提示词不是执行拦截**：本次提示改进不能宣称已经根除错选旧记录。仍需补齐精确提取和运行前身份约束。
2. **数组筛选缺失（33—39 多个场景）**：运行器仅支持点路径和数字索引。模型生成 JSONPath filter、把对象数组 `contains` 当作字段匹配，或错误认为创建响应必然有 `data.id`。这会阻断后续修改、删除。
3. **断言格式错误（30）**：模型连续输出 `["eq", "status_code", 200]`，不符合标准字典式断言。已明确提示标准格式、比较器和选择器支持边界。
4. **删除后空结果误判（31）**：接口实际为业务成功和 `data:null`，模型却猜 404。已人工明确“数据不存在”的断言并真实复测；没有把业务失败简单改成通过。
5. **混合场景鉴权过粗（40）**：场景级布尔值把登录入口也标为必须先有 token，登录前被静态校验拦住。改为冻结按端点划分的认证集合，保留业务目标覆盖及修复时认证要求。

补充复测：更新生成提示后，对子场景 30 明确提供了“按本轮唯一角色名查询、断言结果唯一且名称匹配，再使用 ID”的说明并重新生成。该次仍未成功：三轮分别出现 JSON 语法错误、运行时变量被空配置覆盖、`timestamp_ns` 自引用；均在静态检查阶段停止，没有发出目标业务请求。不能宣称提示改进已解决模型输出质量问题。
