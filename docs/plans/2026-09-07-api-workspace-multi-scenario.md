# API 对话工作区 B：独立场景顺序生成与验证

## 已批准范围

用户确认采用 B：补齐工作区管理，将一次自然语言需求拆成多个独立场景，逐场景生成、验证、有限修复，用户检查后分别保存。不是把全部端点拼成一个长用例。不改变 requests 用例契约；Python 仍支持查看、复制、导出。

本次只修改代码并使用隔离数据库、模拟模型和模拟目标验证；不清理开发数据库，不自动访问用户的 NAS、模型服务或被测接口。部署迁移由用户执行。

## 根因与约束

- 静态检查失败时丢弃候选，下一轮实际拿到空草稿，不能有针对性修复。
- 全局 headers 的变量校验与运行替换不一致，登录后提取的 token 不能在登录前使用。
- 单场景契约接收了多场景需求；原界面既不解释范围，也不保留独立结果。
- 工作区选择器缺少管理入口，工作区标题与正式用例标题混用。

失败证据和可解析草稿必须保留；没有可执行断言不得标记通过，不通过删除断言、复制实际值到预期值等方式伪造成功。静态非法候选不能发请求；服务不可用或执行结果不确定时不盲目重放写操作。

## 数据与执行契约

复用 APIWorkspace 保存根工作区和独立子场景，新增 `parent`、`scenario_order`、`scenario_description`。仅允许一层结构：工作区列表展示根，根详情包含非递归的子场景详情。每个子场景独立持有 draft、candidate、generation、debug 和 saved_case，沿用现有编辑、验证、导出和保存接口。

1. 用户在根工作区选择规范、端点范围、启用的模型，输入测试目标，明确确认试运行目标地址。
2. 模型先给出场景清单及对应端点：`{scenarios:[{title,description,endpoint_ids}],summary}`，每次最多 20 个场景、沿用最多 50 个端点的范围限制。不宣称覆盖所有参数组合。
3. 清单校验通过后先持久化、展示，再依次生成各场景。每个场景自行完成登录及变量提取，不读取其他场景的会话或变量。
4. 每个场景最多 3 轮生成/修复；总时限从根任务排队起计算，子场景不能重置时限。任务重投、版本变化、权限或模型失效均须检查。
5. 一个场景失败保留其草稿和证据，正常情况下继续下一场景；总时限或授权失效时明确终止剩余场景，不能一直显示排队中。
6. 根记录本轮 `scenario_ids`、当前场景和总数；再次生成不静默覆盖以前的子场景及保存结果。
7. 用户可浏览各场景，但根生成期间不能同时修改、调试、修复子场景。结束后可逐场景采用、调试和保存成独立测试用例；不自动覆盖正式用例。

静态失败且尚无可执行候选的场景也有独立恢复入口：明确重新生成本场景，不强制把其他成功场景再跑一遍。子场景保存首次冻结的需求与自身目标，后续修复不使用根工作区后来改写的需求。仅切换子场景模型不改变请求脚本，保留原来仍有效的运行证据；脚本、端点或规范同时修改时不能继承旧验证结论。旧任务仍通过版本和任务标识阻止回写。

根覆盖率分开返回计划覆盖、已生成覆盖、验证通过覆盖的端点集合及数量。计划不是产出，可解析但静态非法草稿不是可执行产出，过期版本不是已验证版本。一次场景失败不将其他成功场景变为失败，也不把整个任务标为全通过。

## 工作区管理与界面

- 明确“当前工作区”选择器，管理弹窗支持重命名与删除。
- 标题独立于用例名称；仅重命名不让脚本验证失效。
- 删除须用户确认，检查所属用户、项目、版本以及根和子任务忙碌状态。只删除工作区、子草稿及对话；不删除正式用例、执行记录、Swagger 或端点。
- 输入区明确“描述测试目标”，增大高度、支持纵向调整，提交失败保留文字。
- 场景清单展示端点、进度、失败原因、覆盖统计，可切换查看各自候选、修改差异、运行日志和 Python。
- 保留本地脏草稿，轮询不得覆盖用户编辑；当前工作区被删除后明确选择下一项或清空。

## 分工与验收

Terra 后端负责模型、迁移、任务编排、管理 API、变量/断言验证和后端单元测试。Terra 前端负责管理、场景切换、状态与交互测试。主 Agent 负责契约、代码审查、独立隔离验收、真实迁移测试与浏览器验收，最后中文提交（排除浏览器 ZIP）。

重点回归：

- 登录 → 提取 token → 后续认证请求，运行时和 Python 导出一致。
- 静态失败的实际草稿进入下一轮提示；失败不会发 HTTP，下一轮能修正；保留以前可执行候选。
- 多场景请求顺序、Session/变量隔离、部分成功、验证与计划覆盖率不混淆。
- 采用/保存独立，改动后的验证失效；重命名不失效；删除不级联正式用例及报告。
- 队列重复投递、总时限、任务撤权、忙碌根/子场景、跨项目/用户与本地编辑保护。
- SQLite 临时库实际应用增量迁移；后端离线测试、前端单测与构建、隔离浏览器完整流程、`git diff --check`。

## 部署与回退

用户在后端虚拟环境执行 `python manage.py migrate api_testing`，然后重启后端与 Celery；Vite 开发模式刷新页面即可，生产模式重新构建前端。

迁移为增量结构，不删旧数据。发现问题先暂停新生成任务，停止 worker 后回退代码；不要在保留子场景数据时直接逆向删除字段。真实模型输出质量、真实目标业务接口覆盖及耗时仍需用户在测试环境验证，离线验收不代表这些外部服务已通过。

## 实施验收结果

- 后端离线回归：540 项通过，覆盖 API、AI 核心、公共组件、计划任务、通知及 WebUI。
- requests 运行器：21 项通过，包括全局/运行时/步骤 headers 覆盖、提取变量及独立 Python 导出一致性。
- 前端：170 项单测及生产构建通过；仍有项目原有的大体积 chunk 构建提示，不影响本次构建。
- 实际增量迁移：临时 SQLite 依次应用 0015～0018，既有用例和执行记录保留；删除工作区仅级联子场景，正式用例仍在。
- 独立多场景验收：静态错误修复、登录 token 提取、独立 Session、顺序请求、中间 503 后继续下一场景、覆盖去重及保存/删除边界通过。
- 浏览器验收：完整生成/采用/调试/修复/保存/导出流程、两个场景分别保存与独立重新生成、子场景换模型保留证明、重命名保留本地编辑、工作区删除保留用例、输入/刷新/已有用例编辑回归通过。
- `git diff --check` 通过。所有测试均使用临时数据库和模拟服务，未验证用户的真实模型、NAS 或被测系统，也未清理开发数据。
