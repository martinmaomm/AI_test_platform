# API 工作区可靠性整改

本次实施保留 B 方案：接口文档、网页采集两个来源汇入同一工作区；JSON 是唯一可执行定义，requests 串行运行，Python 仅查看/复制/导出。候选不直接覆盖正式用例。

## 实施范围

1. 工作区生成试跑和手动调试保存独立平台执行记录；超时、取消保留已完成步骤及未确认的在途请求。网页来源选择后重新计算依赖，防止旧页面覆盖选择。
2. 用户已有断言与 AI 提议分开记录。改变受保护断言时保留候选，明确人工确认后才可采纳验证。失败有写入副作用时停止自动重放；支持显式清理阶段，仅清理本轮已提取身份的数据。
3. 排队、单场景执行、整批执行分别计时。模型只接收当前场景及声明依赖的详细定义，其他已选接口保留轻量目录；完整运行证据仍保存在平台。
4. 网页探索的点击和新窗口首次导航也检查来源范围，不能只检查显式 navigate 工具。Chromium 服务端重定向链并非每一跳都进入 Playwright route；本次不宣称它是完整网络隔离沙箱。曾验证的响应代取方案会改变内网页面网络语义，未采用，不通过重放请求弥补。

## 边界契约

- 每轮结果包含 `execution_id`，工作区 `execution_history` 可追溯历次真实运行；复用现有执行表，不新建平行报告体系。
- `POST workspaces/<id>/cancel/` 携带 `revision`，取消整批或单场景，不终止 Celery 服务。
- 候选 `review.requires_confirmation` 表示断言变动需人工确认，提交 `assertion_review_ack` 与服务器候选 hash 绑定，防止确认过期版本。
- 步骤可声明 `phase: "cleanup"`、`requires: ["created_id"]`；资源身份须来自本轮提取，不能仅凭用户传入旧 ID 授权清理。硬超时或取消不能保证清理，报告必须如实展示。
- `requests_runner` 提供 `on_progress(report)`、`should_cancel()`，底层子进程负责请求，父进程保留检查点并控制生命周期；业务请求仍串行。
- `replay_safety` 描述失败后的重放风险；未知写入结果不能按“没有数据”处理。

## 验收与回退

使用临时 SQLite、模拟模型/HTTP、回环浏览器完成回归；不调用付费模型或修改 NAS 测试数据。覆盖取消竞态、超时保留结果、清理身份、断言确认、来源交接及前端操作。主 Agent 审查后提交中文 commit，并在无在途任务时重启本地服务，用户再做真实模型验收。

无数据库结构变更时直接回退本次代码提交；正在执行的任务先正常结束或取消，避免旧进程继续运行不同版本逻辑。
