# WebUI AI 脚本生成暂停处理与恢复交互设计

状态：已确认并实施
日期：2026-08-30
范围：WebUI AI 脚本生成 V2 的 `needs_input`、`needs_confirmation`、`needs_credentials` 暂停态

## 1. 背景

当前生成任务在安全预检发现歧义、风险或缺少登录信息时，会进入暂停状态，但页面仍把当前阶段显示成“进行中”。用户只能看到通用提示，缺少清晰的待处理事项和“提交后继续”入口。

现有后端状态已经能够区分：

- `needs_input`：场景信息不足；
- `needs_confirmation`：存在歧义或探索阶段写操作风险；
- `needs_credentials`：页面探索需要登录信息。

但现有接口只有创建、查询、取消、保存，没有暂停任务的处理与恢复接口。因此目前的“重新修改描述后发起新任务”只是绕行方式，不是完整交互闭环。

## 2. 目标与非目标

### 2.1 目标

1. 暂停状态必须明确显示为“等待用户处理”，不能继续呈现为运行中。
2. 页面首屏展示暂停原因、具体待处理项和唯一主要操作。
3. 用户在同一生成记录中补充信息后继续，无需重新创建任务。
4. 登录信息仍只保存在 Redis 临时缓存中，不写数据库、日志或页面持久化存储。
5. 重复点击、刷新页面、WebSocket 断开和并发恢复都必须得到确定结果。
6. 探索阶段继续保持只读；人工确认不能授权 MCP 执行业务写操作。

### 2.2 非目标

- 不改变脚本最终执行阶段可以新增、编辑、删除本轮测试数据的能力。
- 不放开上传、付款、审批、发布、批量删除等高风险探索动作。
- 不重构脚本生成、质量检查和自动修复逻辑。
- 不在本次优化中增加通用工作流引擎或多轮聊天系统。

## 3. 方案比较

### 方案 A：仅优化提示，修改后创建新任务

页面列出待确认项，并把原描述回填到输入区；用户修改后重新创建一条生成记录。

优点：改动小，不新增后端恢复接口。
缺点：重复记录多、临时登录信息必须重新输入、用户难以理解“确认”为什么变成“重新开始”，也不能真正恢复同一任务。

### 方案 B：同一记录补充后继续（推荐）

新增暂停处理面板和恢复接口。用户提交补充答案、修订描述或临时登录信息后，原记录回到安全的流水线阶段并继续执行。

优点：符合状态语义，信息和进度连续，刷新后可恢复，审计链清晰。
缺点：需要扩展状态转换、Celery 重新调度、并发保护和测试。

### 方案 C：平台自动采用默认值继续

模型对歧义自动选择默认字段或默认交互后继续。

优点：点击次数最少。
缺点：容易生成错误脚本或误解业务，违背证据驱动和安全预检目标，不采用。

## 4. 推荐交互

### 4.1 页面层级

暂停后，“生成结果”区域顶部显示独立的“需要你处理”卡片，位置高于场景摘要、最终脚本等标签页。

卡片包含：

1. 明确标题，例如“还需要确认 3 项信息”；
2. 暂停原因，不显示内部异常堆栈；
3. 待处理问题列表；
4. 与当前问题类型匹配的输入控件；
5. 一个主要按钮“提交并继续生成”；
6. 一个次要按钮“放弃本次生成”。

页面顶部状态和时间线同步显示“已暂停，等待处理”，停止旋转或进行中动效。当前阶段保留，以便用户知道任务停在哪里。

### 4.2 不同暂停类型

| 状态 / 错误码 | 页面标题 | 用户输入 | 主要操作 |
| --- | --- | --- | --- |
| `needs_input` | 场景信息不足 | 修订后的完整测试描述 | 重新分析并继续 |
| `needs_confirmation` + `INPUT_AMBIGUOUS` | 还需要确认若干信息 | 每个待确认项对应一个答案 | 提交答案并继续 |
| `needs_confirmation` + `EXPLORATION_WRITE_CONFIRMATION_REQUIRED` | 探索阶段包含写操作要求 | 修订描述，并明确探索阶段只读 | 修订后继续 |
| `needs_credentials` | 需要登录信息 | 临时用户名、密码 | 提交登录信息并继续 |

`INPUT_AMBIGUOUS` 的问题优先读取 `scenario_spec.ambiguities`，缺失时回退到 `warnings`，再回退到 `error_message`。不允许显示空白操作卡片。

### 4.3 安全边界

- 对探索阶段写操作，不提供“我已知风险，仍然继续写操作”的按钮。
- 用户只能修订描述，使探索阶段回到只读；正式脚本仍可包含业务写操作和清理逻辑。
- 临时密码输入不回填、不复制、不持久化，页面刷新后需重新输入。
- 补充答案中若检测到疑似账号、密码或 Token，拒绝持久化，并提示改用临时登录信息区域。

## 5. 接口设计

新增接口：

```text
POST /api/v1/projects/{project_id}/web-testing/script-generations/{generation_id}/resolve/
```

请求示例：

```json
{
  "expected_status": "needs_confirmation",
  "expected_revision": 2,
  "description": "可选的完整修订描述",
  "clarification_answers": [
    {
      "question": "编辑用户时新昵称如何生成？",
      "answer": "使用原唯一名称加 _edited 后缀。"
    }
  ],
  "temporary_credentials": {
    "username": "仅本次请求使用",
    "password": "仅本次请求使用"
  }
}
```

约束：

- `expected_status` 和 `expected_revision` 用于阻止旧页面重复恢复已经变化的任务；
- `temporary_credentials` 为只写字段，响应中永不返回；
- 根据当前错误码验证必填内容，拒绝与暂停原因无关的空提交；
- 成功返回更新后的完整生成记录，前端立即恢复轮询；
- 状态已经变化时返回 `409` 和最新安全状态，前端刷新页面数据；
- 非任务发起人仅项目所有者可以处理，沿用现有项目权限规则。

## 6. 持久化与状态机

### 6.1 新增字段

`WebUIScriptGeneration` 增加：

- `revision`：正整数，每次用户处理暂停任务时加一，用于乐观并发控制；
- `clarifications`：JSON 数组，保存脱敏后的问题、答案、处理时间和处理用户；
- `resume_count`：非负整数，记录恢复次数并设置上限。

不保存临时登录信息。原始描述继续保存在 `description_safe`，修订描述覆盖前先把本次差异以脱敏摘要写入 `clarifications`。

### 6.2 恢复路径

- `needs_input`：更新安全描述，清空旧的规范化及下游产物，回到 `normalizing`；
- `needs_confirmation / INPUT_AMBIGUOUS`：把补充答案作为结构化上下文重新规范化，回到 `normalizing`；
- `needs_confirmation / EXPLORATION_WRITE_CONFIRMATION_REQUIRED`：要求提交已改为只读探索的完整描述，回到 `normalizing`；
- `needs_credentials`：写入 Redis 临时凭据，保留 `scenario_spec`，回到 `preflighting`；
- 凭据已经过期时，即使用户处理其他歧义，也同时提示重新提供凭据。

恢复次数建议最多 3 次。超过上限进入 `needs_review`，避免需求规范化与人工补充之间无限循环。

### 6.3 Celery 调度

暂停状态代表上一 Celery 调用已经正常返回，不再占用 Worker。

恢复时在数据库行锁内完成：

1. 校验状态、版本和权限；
2. 写入脱敏补充信息及临时凭据引用；
3. 更新恢复起点和 `revision`；
4. 提交事务后调度新的 Celery 任务；
5. 用新的任务 ID 替换当前 `celery_task_id`，旧任务 ID 仅保留在结构化恢复记录中。

若调度失败，任务进入 `failed / TRANSIENT_SERVICE_ERROR`，页面显示“重新尝试恢复”，不得停留在伪运行状态。

## 7. 前端组件调整

新增：

```text
frontend/src/components/webui-generation/GenerationActionRequired.vue
```

职责：

- 根据 `status + error_code` 渲染对应问题和输入；
- 校验必填答案、修订描述或成对凭据；
- 只向父组件发送结构化处理结果；
- 不把密码写入组件外的持久状态。

调整：

- `GenerationTimeline.vue`：暂停状态使用警告样式和“等待处理”文案；
- `GenerationResultPanel.vue`：把处理卡片放在标签页之前；
- `useWebUIScriptGeneration.js`：增加 `resolving` 与 `resolve()`，成功后恢复轮询；
- `webUIScriptGenerationPresentation.js`：集中维护暂停标题、操作提示和问题回退规则；
- `webTesting.js`：增加恢复接口；
- `WebUIAutoTest.vue`：连接处理事件和成功/失败提示。

## 8. 错误与边界处理

- 重复点击：按钮提交后立即禁用；后端版本校验保证幂等边界。
- 页面刷新：查询接口返回暂停状态、版本和脱敏问题，页面恢复处理卡片；密码不恢复。
- WebSocket 断开：恢复接口响应直接更新本地记录，随后详情轮询兜底。
- 两个页面同时处理：后提交页面收到 `409` 并刷新为最新状态。
- 处理后模型仍返回相同歧义：再次暂停并显示剩余次数，不自动无限重试。
- 用户取消：沿用现有取消语义；取消后的任务不可恢复。
- 任务已完成：恢复接口返回 `409`，不覆盖最终结果。

## 9. 验收标准

1. `needs_*` 页面不再显示为持续运行，也没有“取消生成”主按钮。
2. 用户无需打开“场景摘要”标签即可看到全部待确认项。
3. 当前示例中的 3 个歧义可以逐项填写并在同一记录中继续。
4. `needs_credentials` 提交凭据后从 `preflighting` 继续，不重复调用需求规范化模型。
5. 探索阶段写操作只能通过修订为只读后继续。
6. 刷新页面后问题和状态可恢复，用户名和密码不可恢复。
7. 同一暂停版本只允许成功处理一次；重复请求得到 `409`。
8. 数据库、Celery 参数、WebSocket、日志和前端持久化中均不存在明文密码。
9. 恢复超过 3 次后停止自动循环并进入人工检查。
10. 正常一次生成、取消、保存和刷新恢复流程不受影响。

## 10. 验证与回退

验证包括：

- 后端状态转换、权限、版本冲突、凭据缓存和恢复分支测试；
- 当前三歧义用户管理场景的完整回归；
- 前端暂停卡片、输入校验、重复提交和刷新恢复检查；
- `npm run build`、相关 Django 测试和 `git diff --check`。

回退时可移除前端恢复入口并停用 `resolve` 路由，原有创建、查询、取消和保存接口不变；新增字段保留不会影响旧流程。
