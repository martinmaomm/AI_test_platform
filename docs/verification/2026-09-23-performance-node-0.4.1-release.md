# 性能节点 0.4.1 请求超时配置与发布验收

## 行为与适用范围

原运行时固定使用连接 3 秒、读取 5 秒；单用户验证的 120 秒是整轮执行预算，不能延长单次请求。本次为计划增加 `connect_timeout_seconds` 和 `read_timeout_seconds`，默认 10/30 秒，分别允许 1–60 和 1–120 的整数。现有计划通过 0006 迁移得到默认值，历史运行快照和报告不变。

编辑页说明连接建立与响应读取的含义。读取超时是等待响应数据的最长空闲时间，不是整个请求的总时长。验证与正式压测使用同一配置，运行确认及详情展示当次值；历史快照缺值显示“未记录”。单用户验证仍为一个用户、一轮，整轮最长 120 秒。

计划配置写入 schema 4 快照并参与验证指纹；修改超时后须重新验证节点。Agent 0.4.1、管理协议 3、Locust 2.43.3。0.4.0 节点可继续心跳和显示升级提示，但不能执行新快照。

请求与流式读取统一区分 `connect_timeout`、`read_timeout`、`connection_error`；存在明确异常类证据时区分 DNS/TLS。错误消息只含固定中文及安全异常类名，不拼接原始异常、URL 或凭据。流式响应中断时标记响应不完整，跳过断言与提取，没有新增请求重试。旧记录的泛化网络错误不能追溯成某一种具体超时。

`backend/scripts/test_performance_request_timeouts.py` 使用回环模拟服务，逐项启动真实 Master/Worker：

1. 响应头延迟 6 秒，默认 10/30 秒配置成功。
2. 读取配置 1 秒、响应头延迟 2 秒，记录 `read_timeout`。
3. 返回 HTTP 200 后响应体停顿，记录 `read_timeout` 与不完整响应，断言跳过。
4. 建立连接后直接关闭，记录 `connection_error`。
5. 响应体截断，记录 `connection_error` 与不完整响应。

每项只请求一次。没有访问外部商城，没有发起真实节点压测；实际 TCP 建连超时仅验证异常分类，未用不可控的公网黑洞作计时验收。浏览器截图和原始验收输出留在 Git 忽略的 `backend/temp/`，不包含真实业务账号。
