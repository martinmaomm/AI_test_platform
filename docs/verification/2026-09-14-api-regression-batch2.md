## 4. 待修问题

### D-01 / P1：多场景的目标混入同一个子场景

复现入口：根工作区 23，选择 CRUD 子场景 24 查看三轮生成记录。

预期：CRUD 子场景只负责本轮新分类的增删改查；未认证查询由独立子场景 25 承担。

实际：

- 第 1 轮把“场景2-未认证查询”放在 CRUD 的第 1 步，错误为“候选步骤 1 缺少 OpenAPI security 要求的鉴权参数”。
- 第 2、3 轮将它移到第 8 步，仍保留在 CRUD 内，错误随之变为“候选步骤 8 缺少 OpenAPI security 要求的鉴权参数”。
- 规划层已经正确拆成两个场景，且分别冻结了不同的 `authenticated_endpoint_ids`；独立负向子场景随后一次通过。因此不能把原因归为账号权限不足或 API 不通。

代码检查：`workspace_tasks.py` 创建每个 `child_snapshot` 时复制整份根 `messages`；生成提示同时携带根对话与 `current_scenario`。这与本次混入现象直接相关，但仍须通过定向修复和复测确认收敛效果，不能保证仅改一句提示词就彻底解决。

建议修复方向：子场景输入明确区分“全局约束”与“当前目标”，不要把其他子场景的执行要求当本场景待办；修复反馈需指出跨场景混入，而非只重复“缺鉴权”。保留独立反向场景，不添加固定网站关键词，不弱化鉴权/断言检查。

安全结果：三轮均未进入真实业务执行，资源分类全量读回与运行前一致，没有新增残留。

### D-02 / P1：计划报告显示的成员顺序错误

复现入口：套件 2的顺序为 10→11，对比手动执行报告 78 与计划报告 79、80。

预期：报告的“按执行顺序的子用例结果”也按冻结顺序 10→11 显示。

实际：计划报告显示 11→10。执行快照为 10→11，数据库明细 start/end 时间证明实际按 10→11 串行完成；不是执行器并发或反序运行。

已定位链路：

- `scheduled_tasks/scheduling.py::_create_api_snapshot` 先按 `suite.test_cases.all()` 的默认顺序批量创建明细。
- 随后 `capture_suite_snapshot` 按套件配置排序，但复用前面创建的明细 ID。
- `APITestSuiteExecutionDetailSerializer.get_case_executions` 按明细 `id` 排序返回，不能代表真实冻结顺序。

建议复用统一快照建明细流程，并按冻结序号返回报告；需要补一个“用例创建顺序与套件顺序相反”的定时回归。不得在测试脚本中把反序结果改成期望来制造通过。

截图：[计划报告顺序与配置不符](../../backend/logs/api-regression/20260914-batch2-UnFrk9/schedule-report-order-mismatch.png)。
